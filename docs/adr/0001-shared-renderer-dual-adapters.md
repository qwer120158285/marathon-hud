# 共享绘制模块 + 双端薄适配层

浏览器里的布局编辑器与命令行离线渲染器必须使用同一套绘制逻辑，否则两套实现会长期漂移、预览与成片不再对应。决定抽出一份只依赖标准 Canvas 2D 接口的共享绘制模块，浏览器与 Node 各自提供画布创建、字体注册等薄适配层。

## 技术边界

1. **共享绘制逻辑，不共享运行环境。** 核心模块不得直接引用 `window`、`document`、DOM 或 Node 专有 API；画布创建、字体注册、资源加载由两端适配层提供。
2. **字体必须统一。** 字体文件随项目打包，两端显式注册；必须等字体加载与注册完成后才开始绘制，避免字体回退造成文字尺寸与布局偏移。
3. **Golden Image 不要求逐像素相同。** 不同平台的 Canvas 实现、字体抗锯齿与底层图形库存在细微差异；采用像素差异阈值，并对布局、颜色、位置等关键区域设置更严格的校验。

## 备选方案

CLI 生成图片，编辑器只展示截图。

不选它的原因：编辑器拿不到真正的实时交互预览，调整参数后的反馈链路是割裂的；后续组件调试与布局编辑也难以支持。

## 代价

需要维护双端适配层、字体加载时序，以及视觉一致性测试。

## 验收标准

同一组输入数据，在浏览器与 Node 渲染出的视觉结果必须符合下列容差；布局、颜色、位置等关键区域适用更严格的阈值。

### 字体

- **Inter**，SIL Open Font License 1.1；字体文件随项目打包，不依赖操作系统字体。
- 浏览器与 Node 分别显式注册同一字体文件；固定字体文件版本及 SHA-256，防止日后升级字体导致基准图变化。
- 数字指标启用等宽数字（`tabular-nums`），避免 PACE / HR / CAD 数值跳动时宽度抖动。
- 字体加载与注册完成后才能开始 Golden Image 测试与正式渲染。

### Golden Image 容差

| 校验范围 | 允许差异像素比例 | 单通道最大偏差 |
| --- | --- | --- |
| 全图 | ≤ 1% | ≤ 8/255 |
| 关键区域 | ≤ 0.2% | ≤ 8/255 |

计算口径：

1. 一个像素只要 RGBA 任一通道的绝对偏差 > 8/255，就计为差异像素；**Alpha 通道也参与比较**。
2. 差异像素比例 = 差异像素数 / 当前校验区域总像素数。
3. 全图与关键区域分别计算，不能用全图结果掩盖局部问题。

关键区域由两部分组成：① 每个组件的边界矩形向外扩展 8 px；② 文字实际绘制包围盒及其基线附近的保护带。第二项以文字实际绘制包围盒为基础，而不是只取一条基线，否则会漏掉上升部、下降部与数字边缘。

### 测试矩阵

固定示意数据 × 两个目标预设（抖音竖屏 1080×1920、B 站横屏 1920×1080）各一张基准图；浏览器与 Node 各输出 PNG，与同一基准图比较「全图 + 关键区域」。两端必须使用同一份数据、同一份布局、同一套字体资源、同一组渲染参数；并固定 Canvas 尺寸、设备像素比为 1、颜色空间与透明背景处理方式，避免测试环境差异。

验收：浏览器 Canvas 2D 与 Node `@napi-rs/canvas` 分别与同一基准图比较，均通过上述阈值。

### 基准图维护

未来升级 `@napi-rs/canvas`、底层 Skia 或字体版本，必须重新审查基准图；不能为了让测试通过而随意放宽容差。

## 最终原则

浏览器原型就是最终渲染器的可视化预览，而不是另一套独立实现。

## 修订 1（2026-11-17）：文字区域的比对口径

原始「关键区域 ≤0.2%」在原样涵盖**文字实际绘制包围盒**时无法满足，且不是实现不到位。

### 实测事实

同一字体（Inter 4.1）、同一字号、同一布局，Node（`@napi-rs/canvas`，Skia 自带 FreeType 路径）与
Chrome headless（macOS 上走 CoreText）各出一张 PNG，按原口径比较：

| 区域 | 差异比例（单通道 >8/255，Alpha 参与） |
| --- | --- |
| 全图（不含文字框） | 0.0062% |
| 非文字关键区域（组件矩形外扩 8 px） | 0.1340% |
| 文字实际绘制包围盒 | 13.93% |

差异集中在字形笔画边缘，整体平移 ±2 px 后差异率几乎不变（17.22% → 17.04%），
墨迹质心差 0.29 px、支撑包围盒差 1 px、轮廓距离 0 px —— 即**视觉一致而覆盖值不同**：
两端字形笔画粗细系统性相差约 0.5 px，是光栅化引擎差异，不是绘制错误。

进一步实测「降采样后逐像素」这条路是否可行（2× / 3× / 4× / 6× / 8× / 12×，含整框墨量归一化）：

| 降采样 | 跨光栅器差异 | 换一个数字（配速 5:32 → 5:38） |
| --- | --- | --- |
| 2× / 3× / 4× | 19%–27% | 3.7%–9.3% |
| 6× / 8× | 18.7%–26.5% | 4.1%–9.5% |
| 12×（先整框墨量归一化） | 3.6% | 8.4% |

小窗平均不但没滤掉差异，反而把沿笔画分布的差异摊到更多格子上，导致**判据方向反转**
（正常差异大于真错误）。只有 12× 且先做归一化才能分离，此时一格里已有十余像素，只能当兜底。

### 修订后的验收口径

关键区域仍由「组件边界矩形外扩 8 px ∪ 文字实际绘制包围盒」组成，但**分两类判定**：

| 校验区域 | 判定方式 | 阈值 |
| --- | --- | --- |
| 非文字区域（组件矩形的底板、描边、留白） | 原始像素比较，单通道 >8/255 计差异 | 全图 ≤1%、关键区域 ≤0.2%（不变） |
| 文字区域 · 几何 | 墨迹质心偏移、墨迹支撑包围盒偏差、字形轮廓距离 | 各 ≤1 px |
| 文字区域 · 内容 | 列 / 行墨迹剖面：归一化相关系数与归一化 L1 距离 | 相关 ≥0.98、L1 ≤0.05 |
| 文字区域 · 墨量 | 墨迹总量相对差 | ≤20%（整体兜底） |
| 文字区域 · 粗降采样 | 12× 盒式、整框墨量归一化后逐格 8/255 | 差异格 ≤6% |

标定（同一组 PNG）：

| 指标 | 跨光栅器（应当通过） | 换数字 5:32→5:38（应当失败） |
| --- | --- | --- |
| 剖面相关 | 0.9896 | 0.9588 |
| 剖面 L1 | 0.0385 | 0.0662 |
| 粗降采样差异格 | 4.67% | 8.43% |
| 墨量相对差 | 10.64% | 7.02% |

### 为什么这样分工

- **位置 / 尺寸 / 基线**：几何三项，硬阈值 1 px，不享受任何降采样宽容 —— 修订不放宽这几项。
- **内容（换了哪个数字、哪一行）**：剖面相关与 L1。它们对整体浓淡不敏感，对笔画位置分布敏感；
  换一个数字会让相关掉到 0.9588、L1 升到 0.0662，与跨光栅器差异（0.9896 / 0.0385）分得开。
- **整体浓淡 / 字重**：墨量带。它对「按比例整体变淡」敏感（-50% 会立刻越界），
  对换数字不敏感，正好与上一条互补。
- **兜底**：12× 归一化降采样，抓「文字整段丢失、整体错位、换字号」这类粗错。
- **字体属性**：仍由「随项目打包 + `FONTS.json` 固定版本与 SHA-256 + 两端显式注册」保证。

### 约束（不因本次修订放松）

1. 非文字区域维持原阈值 0.2%，不得上调。
2. 几何三项维持 1 px，不得上调。
3. 阈值只能由实测数据标定得出，且必须有对应的失败用例（`tests/golden.test.mjs`）；
   不得为了让测试变绿而调阈值。
4. 升级 `@napi-rs/canvas`、Skia、Chrome 或字体版本后必须重跑标定并重审本表。
